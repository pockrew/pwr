Self-hosted · v0.1

Every webhook, stored first. Delivered to localhost when you're ready.

PWR is a self-hosted webhook relay. Your server receives and stores provider webhooks; a small agent on your machine delivers them to your local app, keeps the full history, and replays any of them on demand, even offline.

How it works

A durable queue between the internet and your laptop.

Providers talk to a server you control. Your machine only ever makes an outbound connection, so there is no inbound port to open and nothing is lost while you are away.

Features

Built for the webhook you need to debug at 2 a.m.

The small, boring guarantees that make webhook development predictable, in one self-hosted package.

Byte-exact payloads

Bodies are stored and forwarded as the original bytes: never parsed, re-serialized, decompressed, or re-signed. Raw query strings survive too.

Replay, even offline

Re-send any stored delivery to the same endpoint with its current target and secret. Each replay gets its own ID and never touches the original.

Provider signatures

Use a scoped x-api-key, or verify the provider's own signature against the raw body.

GitHubStripeSvixShopifySlackCustom HMAC

Studio inspector

A local UI for headers, bodies, responses, per-endpoint results and side-by-side comparison, served by the agent on loopback.

CLI and MCP

Script everything with pwr. Give AI assistants read access to your webhook history over MCP; replay stays off unless you enable it.

Routing and fan-out

Group endpoints into collections, route by path, and give each matching endpoint its own delivery. Pause and resume without losing anything.

Durable by design

SQLite on both sides, stable IDs, idempotent ACKs. A result that could not be saved is retried as a save, never as a second call to your app.

Edit config offline

Change collections and endpoints without a connection. Conflicts keep your local version and wait for an explicit choice; timestamps never pick a winner.

Retention that keeps its promises

History is pruned by age and count, but never pending work or unreported results. When the disk is full, intake stops safely instead of losing data.

Get started

From install to your first delivery.

Run the server with Docker behind your TLS proxy. Create a tunnel and two keys in Admin, then connect the agent on your machine.

  • Server: cp .env.example .env and docker compose up -d. Admin lives at /admin.
  • Agent: one binary, loopback only, starts on login with pwr agent install-service.
  • Provider: point it at /ingress/my-tunnel/<collection-id> with the inbound key or its signing secret. 
# start the agent and connect a tunnel
$ pwr agent start
$ printf '%s' "$RELAY_KEY" | pwr connect my-tunnel \
    --server https://hooks.example.com --api-key -
● Connected to server tunnel: my-tunnel

# route a collection to your local app
$ pwr collections create my-tunnel payments
$ pwr endpoints create my-tunnel <collection-id> \
    --path /hooks --target http://127.0.0.1:3000/hooks

# watch, inspect, replay
$ pwr studio
$ pwr replay <delivery-id> --tunnel my-tunnel

Security model

Your targets and secrets never leave your machine.

The server routes by collection and path. It never sees your local URLs, target credentials, or response bodies; it only learns whether a delivery succeeded.

  • Agent-owned targets. Target URLs and secrets live only in the agent's database, which is readable by your OS user alone.
  • Loopback only. The agent API binds to 127.0.0.1 and requires a local token; Studio signs in with an HttpOnly cookie.
  • Scoped keys. Separate inbound and outbound keys per tunnel, stored as hashes; signing secrets are encrypted at rest.
  • Outbound only. The agent dials out over HTTPS/WSS. No inbound port on your machine, and one owner per tunnel.

Honest guarantees

Exactly what PWR promises, and what it doesn't.

No marketing math. These are the delivery semantics of v0.1.

At least once

Every call carries X-PWR-Delivery-Id (and X-PWR-Replay-Of for replays) so your handler can deduplicate.

In arrival order

Deliveries on a tunnel run one at a time, in the order the server stored them.

Retries collapse

Provider retries with the same delivery ID are stored once per ingress URL.

No silent retries

A failed target call is recorded as failed. You decide when to replay it.

Not included in v0.1: automatic retries, Windows builds, horizontal server scaling, or synchronous callbacks. See all known limitations →

FAQ

Questions, answered.

Does my machine need to be online when webhooks arrive?

No. Your server stores every event and keeps its deliveries pending. When the agent reconnects, it receives the backlog in order.

Can the server see my local URLs or secrets?

No. Target URLs, target secrets, and response bodies stay in the agent's local database. The server only receives status, latency, and size.

Which providers are supported?

Any provider that can send a custom x-api-key header, plus signed webhooks from GitHub, Stripe, Standard Webhooks/Svix (Clerk, Resend…), Shopify, Slack, and any provider that signs the raw body with a plain HMAC.

What do I need to run it?

A small server with Docker behind a TLS reverse proxy, and a macOS or Linux machine for the agent. The agent and CLI are single binaries; both sides use SQLite.

Is PWR free?

It is source-available under the PolyForm Noncommercial License with a Small Company Permission: free for personal and noncommercial use and for companies of 10 or fewer people, including commercial work. Larger companies need a commercial license.

How do I move a tunnel to another machine?

Connect the new agent with --takeover (or Take over in Studio). The previous agent stops reconnecting to that tunnel, so the two never fight over it.
